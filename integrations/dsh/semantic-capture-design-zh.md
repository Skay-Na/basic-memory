# DSH 语义记忆捕捉设计

状态：核心代码已实现；本机 desktop profile 已配置，更新后的插件尚需重载并完成真实 DSH 会话验收。下文的生命周期及状态模型为实现依据；聊天界面的内部上下文显示仍待实测。

## 目标

让 DSH 在处理用户请求时，像当前 Codex 流程一样判断是否出现值得长期保存的事实、偏好、约束或已确认决策；有候选时先检索并核对已有笔记，再写入明确配置的 Basic Memory 项目；没有候选时记录 `no_memory`；检查或写入失败时保存有范围约束的待重试状态。捕捉判断由当前 DSH 模型结合完整回合上下文完成，插件只负责生命周期、工具、状态与恢复。

这是一项 DSH 专用设计。Codex 的 `UserPromptSubmit` / `Stop`、Hook JSON、`memory_review.py` 和本机回执协议不直接移植。

## 实施前基线

现有 `integrations/dsh/index.js` 已在 `agent/pre-step` 自动检索 `main` 项目，并在 `turn/end` 为成功回合把用户请求及助手最后一条文本写到 `dsh/inbox`，标为 `pending_review`。它提供 `bm_recall`、`bm_capture` 两个工具，但没有语义审查指令、查重后保存流程、回合回执状态机或失败重试队列。因此当前收件箱属于原始记录捕捉，不是 Codex 式语义记忆捕捉。

## 设计原则

1. **模型负责语义判断**：不使用关键词、长度或正则决定是否值得保存；不把完整对话直接变成长期记忆。
2. **插件负责事实状态**：只有 Basic Memory 工具真实返回成功后才能记为已保存；模型报告“已保存”本身不算服务端证明。
3. **项目和运行范围固定**：所有搜索、读取、写入以及待重试记录都绑定 DSH profile、workspace、显式 Basic Memory project 和原始回合身份；不回退到服务端默认项目。
4. **处理记忆作为不可信资料**：召回笔记只能作为参考，不得覆盖当前用户指令或仓库事实。
5. **默认不中断用户请求**：记忆服务故障时继续正常回答，保存可恢复状态，不把记忆捕捉变成任务成功的前置条件。
6. **保留原始收件箱为独立功能**：语义捕捉不应隐式复制整轮对话。旧的逐回合 `pending_review` 收件箱另设开关；迁移期保留现有配置含义，避免静默改变用户数据流。

## 生命周期与流程

### 1. 接收新用户回合

- 用 `session_id + turn` 建立稳定的 `review_id`；同时保存 profile、workspace、project 和状态库记录的版本。
- `agent/pre-step` 只对直接用户消息做一次本轮初始化，并保留现有自动召回逻辑。将一段短的 DSH 专用审查约定加入模型上下文：先解决用户任务，在最终回复前检查本轮长期信息；区分用户确认与候选方案；必要时使用 Basic Memory 工具核对；最后提交 `saved`、`no_memory` 或 `pending` 结果。
- 不把注入的召回内容、插件自己的检查提示、工具输出、推理内容或子 agent 事件当成用户提供的长期事实。

### 2. 模型在正常回合内审查

- **无候选**：调用 `bm_review_complete(status="no_memory", reason=...)`。
- **有候选**：先用 `bm_recall` 搜索，再用新增的 `bm_read` 读取最相关完整笔记，判断是否已存在或需要修订；再使用明确目标 project 的 `bm_review_save` 保存经过提炼的原子记忆。完成全部候选后调用 `bm_review_complete(status="saved", references=[...])`。
- **写入失败或结果不确定**：调用 `bm_review_complete(status="pending", drafts=[...])`。草稿只含待保存的提炼内容及其 project，不保存整份会话。部分候选成功时同时记录已核实的 references 和剩余 drafts。
- 不新增 `bm_capture` 的语义承诺：该手动工具保持“显式原样写一条用户给出的记忆”的用途；自动审查单独使用结构化工具和回执，避免模型把工具调用成功误当成完整回合检查完成。

### 3. 回合结束与漏检恢复

- 在 `agent/turn-stopping` 读取当前 review 状态。若有终态回执则放行；若没有回执，标为 `unresolved`，保留该回合可供后续复核的本机记录，然后放行用户回答。
- 不默认调用 `agent.steer()` 强行追加一次模型步骤。DSH 文档确认它能在 terminal checkpoint 发起额外步骤，但内部消息是否会显示在聊天中、是否与最终答复的可见顺序一致需要单独验证；在 UI 行为验证前不把它当成与 Codex 相同的隐藏续轮。
- 下一次同 profile、同 workspace、同 project 的用户回合，在 `agent/pre-step` 提醒 DSH 复核最多三条到期的 `pending` / `unresolved` 项。复核必须重新检索服务端，避免重复写入；确认已保存、无需保存或再次失败后更新原记录，不生成重复收件箱笔记。
- `turn/end` 仅作为持久回合结果和成功/失败分类依据，不在事件监听器中同步等待远端 MCP 写入；失败回执和捕捉状态由回合内工具及本机状态库负责。

## 工具与状态模型

DSH 私有工具：

- `bm_read`：按检索结果中的 permalink / title 读取一条完整笔记，供模型做重复检查与事实核对。
- `bm_review_save`：限制到配置 project 和 `dsh/remember`，调用 MCP `write_note` 保存模型提炼的内容；插件只在 MCP 明确返回成功后，把实际 permalink / title 写入 review ledger。
- `bm_review_edit`：对已读取的笔记执行带 checksum 的单处文本替换；修改冲突或结果不明确时重新读取，不能盲目重放。
- `bm_review_complete`：接收 `review_id`、状态、原因、已成功 references 和可选结构化 drafts。验证状态跃迁和 project 范围；saved references 必须能对应 ledger 中由插件确认成功的 MCP 写入或已核实存在的笔记，不能让模型直接伪造写入成功。
- `bm_recall` 继续作为有针对性的只读搜索入口；自动召回仍只使用直接用户输入。现有 `bm_capture` 继续用于用户明确要求的手动记忆，不替代 review 专用保存工具。

推荐的逻辑状态：

| 状态 | 含义 |
| --- | --- |
| `collecting` | 当前回合尚未提交语义检查结果 |
| `saved` | 本轮所有候选均已保存或核实已存在，至少保留可追踪引用 |
| `no_memory` | 已完成检查，没有长期信息 |
| `pending` | 有结构化候选未能确认保存，等待安全重试 |
| `unresolved` | 回合结束时未收到检查回执，等待后续回合复核 |
| `expired` | 超过保留期，敏感正文已清除；不代表已保存 |

回执写入需幂等：同一 `review_id` 只能从 `collecting` 写到一个终态；重复提交相同回执可返回原结果，冲突回执不得覆盖。MCP 写入若成功但响应丢失，重试前先以标题/正文范围检索确认，不能盲目重放。

## 本机状态和失败处理

- 使用本机 `~/.dsh/basic-memory/<profile>/reviews.sqlite3`，目录权限 `0700`、文件 `0600`。profile 从显式 `profileName` 或 `DSH_PROFILE` 取得；缺少稳定名称时关闭本地捕捉与恢复，避免混用队列。SQLite 负责事务和持久化；插件重载后真实 DSH 行为仍待验收。
- `pending` 只保存已提炼的候选草稿、准确 project、标题、内容、失败类别、有限重试时间和回合身份。`unresolved` 若需恢复原回合，只保留最小必要的用户/助手文本，设置七天 TTL；到期清除正文但保留不含内容的终态计数。
- 网络失败、token 文件权限错误、远端工具超时都不得记录凭据或正文到日志。错误时放行正常回答；工具必须明确返回“记忆未确认保存”。
- 重试采用按 profile/workspace/project 隔离的退避队列，同一回合最多尝试一次复核；不做后台常驻投递，不跨项目重放。
- 子 agent 回合默认不单独捕捉；主 agent 可以在其自己的当前回合审查用户确认的结论。原始会话 inbox 和语义记忆 ledger 使用不同目录与 metadata，避免混为长期知识。

| 能力 | 当前 DSH | 设计目标 |
| --- | --- | --- |
| 自动召回 | 已实现，混合检索失败或无结果时回退文本检索 | 实际 DSH 会话中验证 |
| 模型结合整轮上下文判断长期价值 | 已注入审查提示 | 实际模型行为待验证 |
| 查重并只写入提炼后的记忆 | 搜索、读取、保存及带版本校验的编辑工具已实现 | 依赖模型正确执行查重 |
| `saved` / `no_memory` / `pending` / `unresolved` 状态 | 本机 SQLite ledger 已实现 | 实际 DSH 回执待验证 |
| 服务失败后限范围复核与退避 | 后续同范围用户回合触发 | 实际重启及网络故障场景待验证 |

这项设计追求语义与可靠性相近，不承诺复用 Codex 的 Hook 机制、回执协议、插件技能加载方式或聊天可见行为。

## 实施切分与验收

1. **API 验证**：已按安装版本对应的 API 实现；仍需确认 `agent/turn-stopping` 消息可见性、tool 输出是否会被 UI 当作普通聊天内容，以及实际插件重载行为。
2. **语义工具与 ledger**：状态迁移、写入响应核对、范围隔离和权限/TTL 已实现，隔离测试覆盖部分路径。
3. **模型审查指令**：审查约定已通过 `agent/pre-step` 加入；真实模型对它和工具的使用效果仍需验证。
4. **恢复路径**：已接入 `agent/turn-stopping` 的 unresolved 记录和下回合有界重试提示。当前不通过 `steer()` 强制补一次漏检。
5. **隔离验收**：使用临时 project 或测试 namespace 验证搜索、写入、重复审查、服务断开、插件重启恢复和清理；真实 `main` 项目只做只读召回，不写临时测试内容。

验收标准：典型长期事实被保存为简洁自包含笔记；普通问答得到 `no_memory`；相同事实不会被重复创建；写入失败有结构化 pending 并能在同范围后续回合安全恢复；漏回执不会阻止正常回答；子 agent 和插件注入材料不会被误捕捉；日志、配置和草稿不泄漏 token。

## DSH API 依据

该设计基于本机安装的 DSH `0.2.1-rc.3` 和对应公开插件文档/源码：

- `agent/pre-step` 是可修改步骤输入的 waterfall；现有插件已使用。
- `agent/turn-stopping` 是在自然停止前触发的串行 terminal checkpoint，可以通过 `agent.steer()` 触发额外步骤。该能力可用，但消息可见性需要在当前 UI 实测。
- `session/event` 提供可回放的用户/助手消息与 `turn/end`；它适合记录回合数据，不应承担可能阻塞的远端 MCP 写入。
- `ctx.systemPrompt.section` 和 `ctx.tools.register` 已由当前插件使用，可承载 DSH 专用审查说明和结果工具。

适配边界以 DSH 安装版本为准，升级后重新核对事件、服务和会话存储契约。不要依赖 DSH 私有源码路径。
