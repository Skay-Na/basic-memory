# 整理 Basic Memory

用户要求检查、去重、连接、整理或清理 Basic Memory 时使用。此技能由 agent 按需执行；它不是后台常驻的 LLM，也不会自动定期扫描整个项目。

## 工作原则

- 先确认 `primaryProject` 和用户要求的主题/目录/时间范围。默认只在主项目内工作；共享项目和其他项目只读，除非用户明确要求写入。
- 先报告后编辑。若用户只要求检查、列出问题或给建议，只做只读审查。若用户明确要求修复，按该范围执行明确、可逆的修改；跨主题批量重组、合并或删除前，先给出具体计划并取得确认。
- 每次只处理一个有边界的范围。搜索结果不足以代表全库时，清楚说明抽样范围，不能声称已审计全部笔记。
- 搜索命中和向量相似度只是候选线索。写关系、合并内容或标记过期前，必须读完整笔记并比较事实、时间范围、来源和适用对象。
- 保留原始证据、稳定标题和可用关系。优先补充明确的状态、关系或导航；不因内容相似就删除笔记。
- 更新前读取完整版本和 checksum；工具支持时使用版本校验，遇到冲突先重读并重做判断，不覆盖他人的新修改。
- **自动维护批次**：当 `bm_memory_maintenance` 因阈值返回有界批次，且用户已启用 `memoryMaintenance` 时，这代表用户已授权本批安全整理。应在当前 Codex 回合内直接完成，不向对话发送整理计划、逐项进度或常规确认请求。仅做有正文证据支持、可逆且不改变笔记身份的整理；不删除笔记、不做不确定合并、不跨项目操作。证据不足或无法安全编辑时保留原文，并且不要把该笔记计为已审阅。完成后准确提交实际处理的 `reviewed_note_ids`。该流程由当前 agent 运行，仍需要有用户触发的 Codex 回合和可用的 MCP，不是常驻后台任务。
- 标题也属于整理范围：若用户要求整理，或自动维护批次明确要求检查标题，应逐篇核对标题是否准确概括正文、具体可检索、简洁且与正文首个 H1 一致。合格标题必须脱离对话上下文也能让人看出笔记主题，优先用简洁的主题短语说明讨论对象、问题或结论；不得直接复制或截断用户请求、回答开头或会话摘要当标题。只修正空标题、默认标题（如 `Untitled`）、UUID/时间戳/路径堆砌、泛化自动收集标题或与正文不符的标题；已有合格标题保持不动。通常控制在 80 个字符以内，避免臆造正文没有支持的主题。
- 修正标题时同步 frontmatter `title` 与首个 H1，并保留原文件路径、permalink、关系及正文事实；除非用户明确要求整理文件名/路径，否则不要为标题调整而移动或重命名文件。可用 `bm_edit` 的 `find_replace` 精确替换唯一的首个 H1，同时传入 `metadata: {"title": "新标题"}` 和刚读取的 `expected_checksum`，以便原位更新且避免覆盖并发修改。若没有 H1 或无法唯一定位，分步使用适合的安全编辑操作；若仍无法安全保留身份，则报告并暂缓该条，不猜造目标路径。

## 审查流程

1. 从用户请求确定范围和目标结果。若只说“整理一下”，先做只读初查，给出有限、具体的问题清单，再确定先处理哪一类。
2. 先做混合搜索发现语义相近笔记，再用标题、全文、元数据或目录查询验证。查精确标题、ID、状态时使用精确查询；找不同措辞表达的重复主题时使用混合查询。
3. 读取候选笔记全文，检查以下问题：
   - **标题不合格**：标题空泛、默认生成、由 UUID/时间戳/文件路径构成、不能概括正文、直接照搬/截断原始请求，或与正文首个 H1 不一致。根据整篇正文可核实的核心主题或结果提出见名知义的简短标题；不要把内容摘要塞进标题。
   - **重复或重叠**：相同事实被多处记录，或不同标题下内容高度重合。
   - **过期或矛盾**：旧配置、偏好或决定与更新内容冲突，且没有标明适用时间或被取代状态。
   - **孤立或缺少关系**：内容与其他已存在主题相连，但没有有用的导航链接。
   - **标签和目录不一致**：同一概念有多个标签写法，或笔记放置位置不符合既定约定。
   - **缺少来源/范围**：无法判断信息是用户确认、仓库证据还是推断，或无法看出其生效范围。
4. 手动只读审查时，用简短清单呈现发现：候选笔记标题/路径、具体证据、可能影响、建议动作和不确定点。自动维护批次按上面的自动维护规则直接执行，不发送计划；不要把不确定的匹配写成已确认重复。
5. 根据授权范围实施。标题修正只改标题元数据和正文首个 H1，不改变文件路径或 permalink；更新前读取完整版本和 checksum，并确认所用写入方式能保留其他 frontmatter、关系与正文。无法安全保留身份时不改写，列为未处理。合并时先确定权威笔记并保留两边仍有效的信息；为旧笔记添加指向新笔记的 `updates`/`supersedes` 关系，按 schema 更新状态，并检查是否有反向链接需要修复。移动笔记前确认 permalink 配置。默认不删除原笔记。
6. 完成后重新读取被修改笔记，报告实际变更、未处理项和检索范围。不要声称后台自动维护或全库一致性已得到保证。

## 常用图关系

- `relates_to`：一般主题关联。
- `extends`：新内容扩展旧内容。
- `implements`：实现某个决定、规范或计划。
- `depends_on`：理解或执行时依赖另一主题。
- `part_of`：明确的层级或组成关系。
- `updates` / `supersedes`：新笔记更新或取代旧笔记。

关系应描述真实语义，不能为了消除孤立状态而随意添加。只有在现有笔记形成清楚主题簇、且用户需要导航入口时才创建 hub/index 笔记。

## 输出格式

只读审查时，给出：审查范围、发现及依据、建议的下一步。执行修改时，额外列出实际改动的笔记和保留/未处理的问题。对没有证据的项目明确写“无法判断”，不要补造原因。
