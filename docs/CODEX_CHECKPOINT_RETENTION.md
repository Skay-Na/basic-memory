# Codex 检查点保留与整理规则

## 目的与边界

Codex checkpoint 是不可变的工作恢复快照。每次压缩仍会产生新的 checkpoint，因此文档数量可能持续增加；本规则降低遗失上下文和搜索噪声的风险，但**不承诺限制总数量**。不以固定数量上限或自动清理来换取表面整洁。

checkpoint 与长期项目记忆用途不同：前者回答“这项工作当时进行到哪里、如何接手”，后者记录当前有效的项目事实、决定和运行说明。完成任务时应先把仍有效的信息更新到对应的权威项目文档或决策笔记，不能把 checkpoint 当作长期事实的唯一来源。

## 整理流程

在任务明确完成、或用户提出整理时，按以下顺序人工检查：

1. 找出该任务的 checkpoint 链，读取最新一份，并确认它指向的代码、决策和项目文档仍可用。
2. 将仍有效的结论更新到已有的权威文档；若没有合适文档，再按项目约定建立主题文档。过时结论应标注为历史或被哪个新决定取代，不要无差别追加。
3. 检查恢复价值：未完成工作、未解决阻塞、尚未落地的决定、仍被引用的 checkpoint 都继续保留为活动恢复线索。
4. 默认不移动、不改写、不删除 checkpoint。只有在用户明确要求整理，或确认检索噪声/存储负担值得处理时，才评估归档；不能仅因文档较旧或数量达到阈值就归档。
5. 若评估归档，先在隔离的测试项目验证移动或归档对原 permalink、WikiLink 关系、全文/语义搜索、文件树/Web UI 的影响，并确认可恢复备份。Basic Memory 的移动行为受 `update_permalinks_on_move` 配置影响；没有验证当前部署设置和实际解析结果前，不对真实笔记批量移动。
6. 先小批量处理，并逐一验证原标识仍可读、搜索结果符合预期、引用关系未断。验证失败则停止，恢复原位置；不得继续扩大范围。

归档只是改变组织方式，不一定减少 Markdown 文件数，也不保证搜索噪声降低。若没有满足上述验证条件的归档方式，就保留原 checkpoint，通过搜索精确标题、permalink、任务关键词或同一会话关系来定位。

## 当前默认

- 每次压缩后仍按 checkpoint 技能创建新的、不可变的恢复记录。
- 不设置“最近 N 份”规则，不运行自动归档或删除。
- 整理时优先更新权威主题文档；旧 checkpoint 保持原样，作为历史证据和恢复线索。
- 是否开发可逆归档或检索过滤机制，留待观察实际 checkpoint 增长和检索质量后再决定。
